> 删掉所有 `<!-- 注释 -->` 和示例段落，逐章填充。需求写进**所属组件的章节**，不进全局 FR 节。

## 0. 方法论总览（阅读后删除本章）

**核心思想（AICLP — AI 闭环编程）**，一个控制回路：

```
FSD(规格) = 设定点 | 固件 = 被控对象 | 测试 = 传感器 | 红 = 误差信号 | AI/工程师 = 控制器
循环退出条件：测试全绿。铁律：没有规格条款就不写代码（No code without a clause）。
```

**需求不是"读起来通顺"就写完的**——它写完的标准是：**一个陌生工程师照着契约能搭出判定 pass/fail 的装置**。

**三条不可违反的纪律**：
1. 每条 Must/Should 需求带**验证契约**（含"禁止出现的后果"，防假阳性通过）
2. 需求 ID 稳定，永不重编；废弃用 `deprecated`/`superseded`，不删除
3. 覆盖率/状态由工具从测试结果**生成**，FSD 里不手填状态列

### 0.1 三平面模型（WHAT / HOW / OPERATE）

| 平面 | 回答的问题 | 本工作台落位 |
|---|---|---|
| **WHAT** | 系统必须为真？ | `docs/FSD.md`（本文件） |
| **HOW** | 怎么构建和变更？ | `docs/Method/`（构建契约、编码规范、测试标准） |
| **OPERATE** | 怎么运行和恢复？ | `docs/UserManual.md`（用户手册，从第一天就有） |

判定顺序（第一个 yes 胜出）：外部可观察 ⇒ FSD；约束代码怎么写/怎么验证 ⇒ Method；指导人怎么运行/恢复 ⇒ 手册；
与 AI 助手协作方式 ⇒ `CLAUDE.md`；过去为何做此决定 ⇒ commit message。

两个判据：
- *黑盒测试员能验证它吗？*（能 ⇒ WHAT）
- *换一种语言重写还会存在吗？*（不会 ⇒ HOW）

### 0.2 复杂度缩放

| 复杂度 | 判断 | 写法 |
|---|---|---|
| **Low**（1–2 外设，如裸机 LED/按键） | 组件 ≤3，无协议 | 可省略 Part 分隔线，章节按 L2→L1→L0 顺序直列 |
| **Medium**（默认，如 OLED+传感器+按键） | 3–8 组件，1–2 个协议 | 完整 Parts 方案，每接口一章 |
| **High**（RTOS 多任务/多外设/通信栈） | >8 组件，≥2 协议 | 完整 Parts + 状态模型 + 逐层 tier 矩阵 |

## 1. 系统概述

- **用途与问题**：这个固件解决什么问题，跑在哪块板上（如 STM32F103C8T6 Blue Pill，72MHz，64KB Flash / 20KB RAM）
- **用户/利益相关方**：谁用、谁验证
- **目标与非目标**：明确列出不做的事（如"不做 OTA"）
- **高层系统流**：上电→初始化→主循环 5 句话描述

## 2. 系统架构

### 2.1 逻辑架构
子系统与数据流（如：传感器采集 → 滤波 → 决策 → 显示/执行）

### 2.2 硬件平台
- MCU 型号与资源预算（Flash/RAM 上限——**构建失败于一个数字，规格就必须写那个数字**）
- 外设连接表（引脚、外设、对端器件）
- 供电/复位/调试口（ST-Link/SWD）

### 2.3 软件架构
模块/任务划分、启动顺序、中断向量占用、低功耗策略、更新模型（无/串口 IAP/OTA）

### 2.4 组件分层（骨架——正文 Parts 与之对应）
严格单向依赖：上层依赖下层，下层绝不依赖上层（用回调/注册钩子反转）。

| 层 | 职责 | 本工作台映射 | 测试方式 |
|---|---|---|---|
| **L2 应用逻辑** | 工程自己的决策函数/状态机 | `modules/` 逻辑类模块（如 toggle、状态机、控制环） | host（纯函数 PC 测试）优先 |
| **L1 接口** | 自写的驱动/协议处理（wire/handler 逻辑自己实现） | `modules/` 驱动类模块（I2C 从设备、UART 协议、OLED、按键） | host（mock 外设）+ bench |
| **L0 基础** | 配置和使用、不实现：CMSIS/HAL/CubeMX 生成、FreeRTOS、标准库 | HAL 库、CubeMX 生成代码 | 传递性测试（不单测） |

> **L0/L1 分界线 = 所有权**：协议/驱动是自己实现并测试的 ⇒ L1；调库/配置就够 ⇒ L0。
> 源布局约定：每个组件映射一个独立模块，L1 的纯逻辑核心抽成自由函数供 host tier 测试。

## 3. 实施阶段

每阶段：范围 · 交付物 · 退出标准 · 依赖
- 3.1 阶段一：基础设施（时钟/串口/调试输出/SysTick）
- 3.2 阶段二：核心功能（逐需求走闭环链）
- 3.3 阶段三：增强（错误处理/负向测试/安全）

## 4. 风险、假设与依赖

- 技术风险（概率/影响/缓解，如 I2C 上拉、供电不足）
- 假设（推断项标 `(assumed)`）
- 外部依赖（工具链版本、库版本）

## 16. 验证与确认

### 16.0 测试架构（tier 映射——与本工作台工具链对接）

| Tier | 执行环境 | 本工作台手段 | 适用层 | 成本 |
|---|---|---|---|---|
| **host** | PC（MSYS2 MinGW） | PC 测试（mock 外设 + X-Macro 注册表），pytest/自研 runner | L1 纯核心、L2 决策逻辑 | 最低，每次变更全跑 |

# 需求质量门（工程内规范，写需求前必读）

## 1. 给每条陈述分类

| 类型 | 含义 | 归属 |
|---|---|---|
| **功能需求** | 外部可观察的系统行为 | FSD |
| **质量需求** | 可测量的性能/可靠性/精度/安全 | FSD |
| **约束** | 对平台/技术/环境的强制限制 | FSD |
| **验证要求** | 强制的方法/tier/证据/验收规则 | FSD |
| **架构决策** | 已批准的结构性设计选择 | Method |
| **实现建议** | 非规范建议，可采纳可改 | Method |
| **假设** | 视为真但未证实 | FSD §4 |
| **未决决策** | 尚未解决的产品/架构问题 | open-issues.md |

反例："按键消抖应做成独立模块"是**架构决策**，不是功能需求——它进了 FSD 就变成不可重谈的结构，并污染测试套件。

## 2. 来源与状态

**Provenance（`source:`）**：`user`（用户直接说）/ `existing-approved-fsd`（来自已批准旧规格）/ `existing-implementation`（代码里观察到——见下规则）/ `derived`（由已批准需求推导）/ `domain-pack`（领域包提议）/ `proposed-by-skill`（AI 补的洞）

**Status（`status:`）**：`proposed`（待接受）/ `approved`（规范）/ `inferred`（推断未证实）/ `detected-in-code`（观察到未裁决）/ `deprecated` / `rejected` / `superseded` / `pending`（被未决决策阻塞）

**两条最重要的规则**：
1. **代码里发现的行为 ≠ 需求**。问它是四者之一：文档化的预期行为（→approved）；只是实现细节（→Method，不进 FSD）；不合规（→改的是**代码**）；孤儿（→删除）
2. **绝不静默发明规范值**。缺超时/容差/默认值/初始状态/重试次数/安全假设时，必须报告缺失；可提议数值但标 `source: proposed-by-skill, status: proposed`，直到被接受。**被静默提升为 approved 的提议阈值，就是规格里没人选过的数字的来源。**

## 3. 十三项质量检查（Must/Should 全部通过）

| # | 检查 | 问题 |
|---|---|---|
| 1 | **原子** | 单个可独立验证的义务？（拆开两个动词/行为+期限/成功+失败/输出列表） |
| 2 | **无歧义** | 胜任的读者有唯一理解？ |
| 3 | **可观察** | 结果能直接观察或通过定义的证据观察？ |
| 4 | **可控制** | 触发条件能被创造或供给？ |
| 5 | **可测量** | 需要的地方有时序/界限/数值/容差？ |
| 6 | **可行** | 系统与现有测试设施能实现并验证它？ |
| 7 | **一致** | 与另一条需求/状态规则/接口/约束冲突？ |
| 8 | **必要** | 有来源或已接受的推导支持？ |
| 9 | **可追溯** | 稳定 ID + 稳定来源？ |
| 10 | **失败已定义** | 错误与不可用条件下行为已规定？ |
| 11 | **状态已定义** | 相关的初始与结果状态已知？ |
| 12 | **按画像安全** | 安全需求源于明确威胁画像？ |
| 13 | **已分类** | 按 §1 分类且归入正确平面？ |

**原子性示例**——"器件应拒绝无效凭据、红灯闪烁、60 秒后重试"是三个独立义务：

```text
FR-PROV-21  无效凭据应被拒绝。
FR-UI-14    拒绝应激活定义的红灯指示。
FR-PROV-22  下一次自动配置尝试应发生在 60 s 后。
```

**门禁失败信号词**（视为缺陷而非风格）：*appropriate, graceful(ly), user-friendly, as needed, if possible, reasonable, sufficient, robust, properly, seamless, optimal, minimal, acceptable, normal operation, best effort*（中文对应：适当/优雅/用户友好/按需/尽可能/合理/充分/健壮/无缝/最佳/最小/可接受/正常工作/尽力而为）。
空泛量词同样不合格："数据不丢失"必须给窗口与保证；"可能丢包"是观察不是预期——写明允许丢几个包、超几帧判失败。

## 4. 验证契约（每条 approved 的 Must/Should 都必须有）

> **写契约本身就是可测性检查**——写不出来 = 需求没写完。契约属于需求，不属于下游测试环节。

### 4.1 完整 YAML 形式（假阳性通过可能成立时用）

适用于：恢复、重连、回滚、故障转移——**快乐路径的观察结果恰好也能由被测的失败达成**的场景。

```yaml
id: FR-UART-08
type: functional
priority: must
source: user
status: approved
text: >
  当配置的 UART 主机恢复可达后，设备应在 30 s 内重新建立协议会话
  并恢复有效遥测发布，无需重启。
verification:
  preconditions:          # 刺激前的状态
    - 设备已连接主机，协议会话活跃，遥测正常发布
  stimulus:               # 对系统做了什么
    - 断开主机串口线（或主机停止应答）
    - 保持不可用 10 s
    - 恢复连接
  expected_observations:  # 外部观察者能看到什么
    - 设备检测到会话丢失
    - 其余外设功能保持运行（OLED 正常刷新）
    - 新的协议会话建立
    - 恢复后 30 s 内收到有效遥测帧
  timing: 30 s（从恢复起到首帧有效遥测）
  tolerance: ±5 s
  prohibited_outcomes:    # 即使满足期限也判失败的结果
    - 设备重启（复位计数增加）
    - 需要人工重新插拔/重新初始化
    - 把陈旧或损坏的帧当作恢复证据接受
  tier: bench
  evidence:               # 证明它通过的证据
    - 断开/恢复时间戳
    - 恢复后首帧有效遥测
    - 复位原因寄存器（RCC_CSR）或 boot 计数读数
    - semihosting/串口诊断日志
  cleanup:                # 事后如何恢复
    - 确保串口连接正常
    - 恢复设备到运行基线
```

**`prohibited_outcomes` 不是装饰**：只检查"30 秒内恢复了"的重连测试，在设备**靠重启**恢复时也会通过——而那通常正是被测的缺陷。

### 4.2 紧凑表格形式（其余需求）

一条一行，放在所属章节内。**"Must NOT happen" 列两种形式都不可省略**——去掉它契约就只是描述。

```markdown
| ID | 前提 · 刺激 | 预期观察 | 禁止发生 | Tier |
|---|---|---|---|---|
| FR-GPIO-05 | 喂一个缺 `U2` 的帧 | 载荷中无 `U2` | `U2` 以 0 或陈旧值出现 | host |
| FR-TGL-01 | 上电默认态下按按键 | 输出翻转一次并落盘 | 翻转两次（抖动未消） | bench |
| FR-ADC-02 | 输入 3.3V 校准源 | 原始值在 [4058, 4094] | 超界且无错误标志 | host |
```

有期限才加时间列；每行都挂空时间列会训练读者无视它。

**汇报时说明分界**："8 条完整契约，85 条紧凑"——让审查者知道风险判断在哪里，并允许他们不同意。

# STM32 领域包（示例需求库，提议不采纳）

> 用法：匹配本工程场景的需求可直接引用改写；`source: domain-pack`。每类 1–2 条示例，展示"可证伪"怎么写。

## A. GPIO / 按键

```yaml
id: FR-GPIO-01
type: functional
priority: must
source: domain-pack
status: proposed
text: >
  按键按下时，系统应在去抖窗口（10 ms ± 2 ms）内检测到稳定电平，
  并只在电平翻转后沿触发一次事件。
verification:
  preconditions:
    - 按键引脚配置为上拉输入，去抖使能
  stimulus:
    - 以 5 ms 间隔的抖动序列按下（机械抖动仿真：高/低交替 6 次后稳定）
  expected_observations:
    - 恰好一次按键事件
  prohibited_outcomes:
    - 抖动期间多次触发
    - 事件在 8 ms 内（去抖窗口外）产生
  tier: host            # 抖动序列可在 PC 上以 mock GPIO 输入仿真
  evidence: 事件计数器 + 时间戳
  cleanup: 释放按键，返回初始状态
```

## B. UART 协议解码

```yaml
id: FR-UART-03
type: functional
priority: must
source: domain-pack
status: proposed
text: >
  收到完整合法帧（帧头 0xAA 0x55 + 长度 + CRC16）后，解码器应在
  100 ms 内输出解析结果；CRC 错误的帧应被丢弃且不影响下一帧。
verification:
  preconditions:
    - 解码器空闲，环形缓冲就绪
  stimulus:
    - 注入合法帧 A；再注入 CRC 损坏帧 B；再注入合法帧 C
  expected_observations:
    - 帧 A、C 输出正确解析结果；帧 B 无输出
  prohibited_outcomes:

  tier: host            # 纯编解码逻辑，PC 测试即完整验证

```

# 与本工作台工具链对接（工程内规范）

## 1. 需求 → 测试的闭环链（逐需求走，不是按项目阶段批量走）

```
契约(FSD) → 测试在 test-plan 声明 → 可执行测试(标 WILL_FAIL/xfail)
  → 代码 → 构建(Keil) → 烧录(ST-Link) → 真机验证(verify.py)
  → 记录结果+提交 → 绿
```

- **可执行测试先于代码写**（或与代码同写），绝不后补——后补的测试断言的是代码恰好做的事，包括 bug
- 功能未实现的测试标 `WILL_FAIL`/xfail：套件保持绿、测试存在、功能落地时 **XPASS 就是落地信号**
- host tier 例外：全套每次变更全跑，红了就不许开始硬件会话
- 真机会话以"旅程测试"（上电→初始化→各功能冒烟）为门：旅程红的时候后面的结果都不可读——一片红可能只有一个原因

## 2. 证据与判定（对照 verify.py 现有实现）

| 验证手段 | 采集什么 | 对应 verify.py |
|---|---|---|
| host PC 测试 | mock 外设 + 断言输出 | PC 测试套件（57/57 基线） |
| semihosting | BKPT 0xAB 采集 printf（`__use_no_semihosting` 修复后独立可跑） | capture 环节 |
| 真机观察 | 复位计数、RCC_CSR 复位原因、心跳节奏（实测 3.3 s）、GPIO 电平 | verify 判定（PASS / TIMING_FAIL） |
| HardFault | C 级 Handler 现场打印 + 寄存器转储 + 符号表解析 | hardfault.py 自动诊断 |

- **判定要写在契约里，不是验证时临场发挥**——契约的 expected/prohibited 就是 verify.py 的断言依据
- 负向判定（TIMING_FAIL、捕获空不误报）与契约的 `prohibited_outcomes` 一一对应
- 结果落盘到 `.workbench/feedback`，反馈闭环按 feedback-log 规范处理

## 3. 发布门禁（建议）

- 开发版本号用 `git describe` 标识，**构建期间不打 tag**；tag 命名空间只装发布
- `git tag` 是人的动作，发生在"需求全绿 + 追溯无缺口"宣布之后
- 打 tag 后对**发布的字节**重跑一遍完整 verify 流水线，红就不发
- 发布验证时板子没接电 = `not done`（附原因），不是 `failed`——通电重跑即可

## 4. 变更请求（任何新功能进入的通道）

**没有条款就没有代码。** 未被任何需求覆盖的工作被拒绝，先走定义：
1. 起草增量需求（走十三项检查 + 契约）
2. 影响分析：牵动哪些现有需求/模块
3. 完成判据 = **需求达成 且 旅程测试仍全绿**
4. 增量进 FSD（update 模式：外科手术式修改，绝不整文件重生成、绝不重编稳定 ID）
